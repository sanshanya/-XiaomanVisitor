# 小满立绘：原因、证据与性能取舍

记录范围截至 0.0.3.4。当前架构与流程以[项目手册](项目手册.md)为准；本页保留已确认事实与当时取舍，不作为另一份实时项目说明。

0.0.3.3 的原生渲染方案已获得作者“效果不错”的画面反馈，保存为 Git 基线 `baseline/native-render-0.0.3.3`，对应提交 `bfe2832`。安装包已另作逐文件校验的 ZIP 备份。0.0.3.4 只整理实现，保留人物素材、大小、位置、表情、口型和交易剧情。

已确认的事实

| 事实 | 证据与边界 |
| --- | --- |
| 问题已存在于已发布的 0.0.2 | 作者使用原始旧包和工坊订阅版都复现；单纯回退代码与贴图未解决。尚不能锁定最早引入的提交。 |
| 普通视窗与放大视窗使用不同摄像机 | 当前游戏场景序列化数据：Emporium_camera 的 PixelPerfectCamera 默认启用，Shooting_camera 上同组件默认停用。 |
| 原生像素相机会损失更细的角色像素 | 当前游戏 DLL 的 CalculateCameraProperties 实际离线计算：16:9 的 1080p、4K 都产生 960×540 中间画面，再放大输出。 |
| 给素材加分辨率不能绕过后面的降采样 | 角色世界尺寸保持不变时，更高分图集仍会先缩到同一低分目标。当前图集已经是 Point、单级纹理；mipmap 不是这次剩余模糊的解释。 |
| 修正后走的是完整原生人物流程 | 保留 StoreClientMono.image、Sprites/SolidBlend 材质、原生走动与暗影渐亮、前景排序。额外 UI 立绘与手动裁切已撤下。 |
| 实机确实按屏幕尺寸渲染 | 0.0.3.3 日志记录 1920×1080、2560×1440、3840×2160 的 native output，pixelCameraEnabled=False；有作者提供的清晰画面。 |
| 离场不能只看“当前顾客” | 原生 DismissCurrentClient 在开始走出前清空 currentClientInstance，所以采样范围还要识别正在显示的小满图集，直到人物隐藏。 |

原生资料来自本机 0.46D 游戏程序集与场景；没有把反编译程序集或完整游戏源码放入仓库。[实测日志摘录与版本哈希](evidence/native-rendering-0.0.3.3.json) 保留了可核对的依据。旧 UI 方案的具体裁切误差没有继续做单独证明，不能把推测写成已确认原因。

当前实现与保留理由

人物仍由一个原生 SpriteRenderer 绘制。普通店铺出现小满时，临时使用游戏本来就支持的非像素相机模式，并通过 LetterboxManager 保持取景，按 EmporiumOption 的原生做法刷新 Outliner。人物隐藏、进入放大/射击视窗、离开店铺或停用模组时恢复。不会改写玩家保存的显示选项。

两个原生钩子继续保留：进场钩子保证第一帧就准备好；显示设置钩子记住玩家在接待期间的新选择，避免离场后恢复成旧选择。状态快照、幂等恢复和离场图集识别都有实际作用，不能为了缩短代码删除。

0.0.3.4 的整理内容：

- 移除临时 OnPostRender 观察组件及逐帧回退诊断字符串；实际输出证据保留在基线资料中。
- 相机、像素相机、Outliner 在绑定时缓存；每帧不再重复 GetComponent。
- 进场时保留一次素材准备，平时由既有动画器维护；删除控制器中的重复 EnsurePortraits。
- 用所属图集识别正在离场的立绘，替代逐帧遍历十八张表情。
- 合并店铺和酒馆的高清图集加载与释放。优先使用已确认的柔和图集，失败时尝试最近邻后备，最后回退低分图；正常情况仍只载入一套高清图集。这不应被宣传为比 0.0.3.3 新节省了一整套图集。
- 原生像素相机本来就关闭时，不重复重建 Outliner；如接待期间确实改变了模式，则完整恢复。

性能代价的范围

调整作用于整台店铺主摄像机，包含它绘制的背景、人物和前景。它不是只给小满单独超采样。UI、音频、剧情逻辑等不因此按同一倍率增加。

| 标准 16:9 分辨率 | 原生默认主场景目标 | 修正后的主场景目标 | 像素面积比 |
| --- | --- | --- | --- |
| 1920×1080 | 960×540 | 1920×1080 | 4 倍 |
| 2560×1440 | 2560×1440（原生已停用像素相机） | 2560×1440 | 1 倍 |
| 3840×2160 | 960×540 | 3840×2160 | 16 倍 |

上述倍率是像素面积计算，不是 FPS 或整帧耗时的测量。窗口、黑边及其他模组改变相机状态时，应以实际状态为准。

共享图集为 2304×2064，按 RGBA32 单级纹理计算约 **18.14 MiB**；磁盘 PNG 约 **0.53 MiB**。18 张表情是同一张图集中的十八个矩形，不是十八份独立纹理。店铺与酒馆共用这份资源，CPU 可读像素副本关闭；加载时仍有临时解码内存。

若只按一个 RGBA32 颜色缓冲估算，960×540 约 **1.98 MiB**，4K 约 **31.64 MiB**，差约 **29.66 MiB**。这不是显存实测；深度、HDR、MSAA、轮廓中间目标和驱动开销都可能改变总量。[可复算尺寸与公式输入](evidence/rendering-cost-estimates.json) 单独保存。

取舍结论

保留当前按人物出现范围切换的原生方案。它已得到画面验证，移动、渐亮和遮挡都继续交给游戏处理。后续默认不使用独立 UI 肖像、手动柜台遮罩，也不永久关闭整局的像素相机。

现有硬件回退检查针对最大纹理尺寸，不测量剩余显存，也不判断显卡性能。

现在没有同存档、同场景、同分辨率的 GPU 帧时或 FPS A/B 数据，因此不能承诺性能损耗很小。后续若有低性能设备反馈，优先考虑一个可关闭高清采样的选项；不要根据主观感觉自动切换，以免重现清晰度跳变。单独重画人物的额外相机可能减少像素工作量，但会重新引入排序、遮挡、渐亮与兼容维护，当前证据不足以支持这份复杂度。

后续性能测试应使用只切换采样模式的开发构建，固定存档、位置、分辨率和帧率上限，分别记录原生采样与高清采样的稳定 GPU 帧时、低帧与显存峰值；走动、交易、特殊视窗和离场恢复另作功能验收。0.0.3.4 的离线检查只证明规则和资源兼容，不替代其自身的实机验收。
